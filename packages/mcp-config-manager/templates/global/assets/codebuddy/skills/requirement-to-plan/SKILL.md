# 需求实现工作流

> **团队配置**：本 Skill 依赖 `../team-config.md` 中的以下配置项：
>
> - 一、项目信息 → 目录约定、组件依赖
> - 二、JIRA 配置 → 项目 Key
> - 五、工具链 & CLI
> - 六、MCP 服务器 → Atlassian、MasterGo
> - 七、设计工具 → MasterGo
> - 八、路由 & 代码定位约定

将"一句话需求"自动转化为包含需求分析、接口清单、设计参考、组件拆分、实现步骤的结构化开发计划。

## ⚠️ 触发规则

当用户消息匹配以下任一模式时，**必须先加载本 Skill，再执行任何其他操作**：

- "帮我实现……需求"
- "开发……功能"
- "实现……功能"
- "我要开发……"
- "帮我做……需求"
- "帮我开发……"

**禁止行为**：匹配上述模式后，**不得先调用 code-explorer 探索代码库**。正确做法：`use_skill("requirement-to-plan")` → 严格按 1→2→3→4 步顺序执行。

## 前置条件

- **Atlassian MCP** — `mcp.json` 中已配置 `atlassian` 服务器（Jira + Confluence），含有效的 `JIRA_PERSONAL_TOKEN` 和 `CONFLUENCE_PERSONAL_TOKEN`
- **Swagger 网关** — （见团队配置：五、配置文件） 中已配置 Swagger 网关地址
- 已执行 （见团队配置：五、工具链 → taxjoy-codebuddy-config） `--global` 安装 MCP 工具
- 已在项目中执行 （见团队配置：五、工具链 → taxjoy-codebuddy-config） 同步编码规范

## 工作流

### 第 1 步：获取需求文档

使用 `confluence-requirements` skill 的 **MCP 方式**（通过 `atlassian` MCP Server）：

1. **搜索需求**：用 `confluence_search` MCP 工具搜索
   ```
   confluence_search(query="用户提供的关键词", limit=10)
   ```
2. **确认目标**：
   - 搜索结果为 **0** → 告知用户未找到，请求更精确的关键词或 Confluence 页面链接
   - 搜索结果 **只有 1 条** → 直接获取该页面内容
   - 搜索结果 **≥ 2 条** → 以列表形式展示（序号、标题、空间、最后修改时间），用 `ask_followup_question` 让用户选择目标文档
3. **确定需求目录**：从搜索结果的标题中提取需求名称（去除空格和特殊字符，取前 20 字），创建目录：

   ```bash
   mkdir -p "（见团队配置：一、需求文档存放目录）/<需求名称>"
   ```

   将此目录路径记为 `$DEMAND_DIR`，后续所有产出文件均存放于此。

4. **获取内容并保存为 PRD**：用 `confluence_get_page` MCP 工具获取 Markdown 格式内容，再用 `write_to_file` 保存
   ```
   confluence_get_page(page_id="<pageId>", convert_to_markdown=true)
   ↓
   write_to_file(filePath="$DEMAND_DIR/PRD.md", content=<MCP 返回的 Markdown>)
   ```
   📎 **留意 PRD 中的 MasterGo 链接**：Confluence 页面可能已包含设计稿链接，第 3 步会自动扫描提取。

### 第 2 步：获取接口文档

分析需求文档，提取需要对接的后端 API。**优先使用 Knife4j 网关快速定位工作流**：

#### 2.1 提取接口关键词

从需求中识别涉及的功能模块，提取中文搜索关键词（如"审批流程"→"审批"、"核算主体管理"→"核算"、"文件上传"→"文件"）。

#### 2.2 检查项目现有 API 封装

**先用 2.1 提取的关键词搜索项目 （见团队配置：一、API 封装目录） 目录**，检查是否已有现成的接口封装可直接复用：

```bash
# 搜索 API 文件中匹配关键词的函数和注释
grep -rn "<关键词>" （见团队配置：一、API 封装目录） --include="*.ts"
```

**搜索策略**：

- 按**中文关键词**搜索注释和 JSDoc（如"公司列表"、"字典"、"权限"）
- 按**英文路径片段**搜索 URL（如 `company`、`dict`、`permission`）
- 优先搜索 （见团队配置：一、公共接口目录）（公共接口集中在此目录）

**结果处理**：

- **找到匹配** → 记录函数名和签名，标注为"✅ 已有封装"，直接在开发计划中引用
- **未找到** → 标注为"🔍 需对接"，进入 2.3~2.7 从 Swagger 获取

> **常见公共接口参考**（通常已在 （见团队配置：一、公共接口目录） 中封装）：
> 字典获取、公司列表/详情、文件上传/下载、租户/用户/角色列表、权限按钮等

#### 2.3 获取网关地址（必须先执行）

**先从项目根目录的 （见团队配置：五、配置文件） 读取 Swagger 网关地址**：

```bash
# 读取网关配置
grep -A2 '"swagger"' （见团队配置：五、配置文件） | grep '"gateway"'
```

如果读取失败，则询问用户提供 Knife4j 网关地址。

#### 2.4 发现服务实际端点（必须先执行）

不同服务可能使用不同版本的 Swagger 端点（`/v2/api-docs` 或 `/v3/api-docs`），**不能猜测版本**。用 `services --detail` 列出所有微服务及其确切的 API 文档路径：

```bash
node （见团队配置：五、Swagger CLI 工具） services --gateway "<从配置文件读取的gateway>" --detail
```

从输出中定位目标服务，**严格使用 `API 文档地址` 列显示的路径**（如 `/v3/api-docs?group=restApi`），后续 `list`/`detail`/`fetch` 等命令拼接 `gateway + 该路径` 使用。

#### 2.5 快速定位：跨服务搜索标签

使用 `swagger-api-docs` skill 的 `search-tags` 命令，在所有 restApi 服务中搜索匹配的标签分组：

```bash
node （见团队配置：五、Swagger CLI 工具） search-tags --gateway "<从配置文件读取的gateway>" --query "<提取的关键词>"
```

**搜索结果处理**：

- **找到匹配标签**（如 `pm-flow-rest → 审批中心 (13个接口)`）→ 进入 2.6
- **无结果** → 尝试换关键词重新搜索，或跳过此步骤标注"缺少接口文档"

#### 2.6 查看分组接口列表

对 `search-tags` 定位到的服务，用 `list --tag` 查看分组下所有接口：

```bash
node （见团队配置：五、Swagger CLI 工具） list --url "<服务restApi地址>" --tag "<标签名>"
```

#### 2.7 获取接口详情（按需）

对关键接口用 `detail` 获取请求/响应结构：

```bash
node （见团队配置：五、Swagger CLI 工具） detail --url "<服务restApi地址>" --path "<路径>" --method <方法>
```

#### 备用：单服务搜索

如果网关不可用或已经知道目标服务，可对单个服务用 `search` 命令搜索接口：

```bash
node （见团队配置：五、Swagger CLI 工具） search --url "<网关地址>/<服务路径>" --query "<关键词>"
```

**注意**：如果 （见团队配置：五、配置文件） 中未配置 Swagger gateway，或搜索无结果，则跳过此步骤并标注"缺少接口文档"。

#### ⚠️ 2.8 保存接口文档（强制执行，不可跳过）

> **swagger_client 所有命令仅输出到 stdout，绝不自动写文件。** 你已经在上面各子步骤中通过终端看到了 swagger 命令的输出结果，现在必须：

1. 汇总 2.2（已有封装）、2.5（search-tags 结果）、2.6（list 结果）、2.7（detail 结果）的所有信息
2. 整理为 Markdown 格式的接口文档（包含"✅ 已有封装"和"🔍 需对接"两部分）
3. **立即调用 `write_to_file` 保存文件**：

```
write_to_file(
  filePath = "$DEMAND_DIR/API文档.md",
  content = <汇总后的完整 Markdown 内容>
)
```

> **禁止行为**：不得假设 swagger 命令已自动保存文件。必须显式调用 `write_to_file`。
> **验证**：保存后确认文件存在。

> ⚠️ **检查点**：第 2 步完成，API文档.md 已保存。**接下来必须执行第 3 步（设计稿）**，禁止直接跳到第 4 步生成计划。

### 第 3 步：获取设计稿（不可跳过）

**本步骤必须执行**。即使最终结论是"无需设计稿"，也必须经过分析判断并输出结论，不可直接跳过。

**先分析需求是否涉及 UI 变更**，再决定是否需要设计稿：

- **纯逻辑改动**（如接口调整、数据处理、状态管理、Bug 修复、权限控制等）→ **直接跳过**，标注"纯逻辑改动，无需设计稿"
- **涉及 UI 变更**（如新增页面、修改布局、新增组件、调整交互等）→ 进入设计稿获取流程：

#### 3.1 自动扫描 PRD 中的设计稿链接

Confluence PRD 中通常已包含 MasterGo 链接。**先扫描 `$DEMAND_DIR/PRD.md`**，搜索 MasterGo 链接：

```bash
grep -oE 'https?://mastergo\.com/[^ )\n]+' "$DEMAND_DIR/PRD.md"
```

MasterGo URL 常见格式：

| URL 模式                                        | 提取方式                                                  |
| ----------------------------------------------- | --------------------------------------------------------- |
| `mastergo.com/file/<fileId>?layer_id=<layerId>` | `fileId` = URL 路径第 2 段，`layerId` = `layer_id` 参数值 |
| `mastergo.com/goto/<shortLink>`                 | 直接作为 `shortLink` 传入 MCP 工具                        |

**结果处理**：

- **找到链接** → 自动提取 `fileId` + `layerId`（或 `shortLink`），告知用户"PRD 中发现设计稿链接，是否使用？"
- **未找到** → 进入 3.2 引导用户提供

#### 3.2 引导用户提供设计稿

PRD 中无设计稿链接时，提供上下文帮助用户定位：

```
该需求属于「<模块名>」模块，需求名称为「<需求名称>」，
请提供对应的 MasterGo 设计稿链接（file 链接或 goto 短链接均可）。
```

- **用户提供链接** → 提取参数，进入 3.3
- **用户明确无设计稿** → 跳过，标注"无设计稿，功能优先实现"

#### 3.3 获取设计稿内容

使用 `mastergo-magic-mcp` 工具获取：

1. **`mcp__getMeta`** — 获取设计稿结构和页面规则
   - **保存**：将 Meta 输出整理为 Markdown，**立即调用 `write_to_file` 保存到 `$DEMAND_DIR/设计稿.md`**
   - 内容包括：页面列表、布局结构、节点层级、样式规则等
2. **`mcp__getDesignSections`** — 获取各 Section 的布局和 DSL（按需，UI 复杂度高时使用）
3. **`mcp__getD2c`** — 获取设计转代码参考（按需，有具体组件时使用）

> 优先使用 `mcp__getMeta` 获取全局结构并保存为文件，再根据需要深入具体区域。

## 注意事项

- **严禁跳过工作流步骤**：第 1→2→3→4 步必须顺序执行，禁止跳过任何步骤。第 3 步无论结论如何都必须显式执行并输出判断。
- **不要跳过确认环节**：需求文档多结果时务必让用户确认
- **不要猜测接口**：以 Swagger 文档为准，没有就标注缺失
- **不要凭空设计**：有设计稿则严格参照，没有则标注
- **遵循编码规范**：计划中的实现建议需符合 `coding-standards` 规则（awaitWrapper、组件优先级等）
- **文档位置统一**：所有产出文件统一放在 （见团队配置：一、需求文档存放目录） 目录下，需求名称在第 1 步从 Confluence 页面标题提取。预期产出文件：
  - `PRD.md` — 需求文档（第 1 步）
  - `API文档.md` — 接口文档（第 2 步）
  - `设计稿.md` — 设计稿 Meta 信息（第 3 步，仅 UI 变更时生成）
  - `开发计划.md` — 结构化开发计划（第 4 步）
- **保存后告知用户**：计划保存成功后，告知文件路径并询问用户是否开始实现
